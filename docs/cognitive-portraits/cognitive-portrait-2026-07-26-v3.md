[建议] 停止条件：若连续两周主交付未完成，暂停探索配额一周，优先恢复闭环。

### 4.2 决策树：下一步行动选择

[建议] 使用下列决策树，不增加额外分支。

```text
收到一个新任务
│
├─ 是否阻塞生产、数据正确性、安全或当周硬期限？
│  ├─ 是 → 进入维护槽
│  │       ├─ 根因已复现？
│  │       │  ├─ 否 → deep_inquiry：复现 → 单一假设 → 验证
│  │       │  └─ 是 → 修复 → 测试 → 交付证据
│  │       └─ 修复后关闭，不扩展相邻改进
│  └─ 否
│
├─ 是否直接推进本周唯一主交付？
│  ├─ 是 → 进入主线槽
│  │       ├─ 边界和验收清晰？
│  │       │  ├─ 是 → delegation 或直接执行
│  │       │  └─ 否 → 先补目标、边界、验收、回报码点
│  │       └─ 完成后必须留下测试、SHA、URL 或报告路径
│  └─ 否
│
├─ 是否属于已安排的 90 分钟探索窗口？
│  ├─ 是 → 进入支线槽
│  │       ├─ 输出继续 / 停止 / 转项目
│  │       └─ 不自动转成 backlog
│  └─ 否
│
└─ 放入候选池
        ├─ 替换现有槽位后才能启动
        └─ 7 天未被选择则关闭或归档
```

[事实] 该树把所有工作限制在维护、主线、支线、候选池四种状态。

[推断，置信度：高] 最关键的控制点不是“如何开始”，而是“没有槽位就不开始”。

[建议] 若任务同时属于多个分支，以安全与数据正确性优先，其次是硬期限，最后才是探索。

[建议] 若根因没有复现，不得跳到“修复”分支。

[建议] 若验证证据不存在，不得把主线任务标记为完成。

[建议] 若候选池条目 7 天未被选择，默认关闭，而不是长期保留。

[建议] 指标 3：至少沉淀 3 条有事后证据支持的判断规则。

[建议] 动作 1：删除没有改变行为的模板字段。

[建议] 动作 2：把重复三次以上且稳定有效的流程封装为 skill 或自动检查。

[建议] 动作 3：保留人工停止开关与失败回报码点。

[建议] 验收：新机制不依赖静默降级，失败时明确报错或停止。
