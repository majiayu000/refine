## 1.3 双环学习

### 单环 vs 双环比例

**单环学习（修正行为，保持假设不变）**：

[事实] 全局 6257 bugfixes / 19584 decisions = **0.320 bug/decision 比**（Δ 0321: 0.42→0.32，-24%）。
[事实] bugfix 密度最高的项目：harness 704 bugfix / 259 session = **2.72**；om 436/117=3.73；x 390/717=0.544；xhh 331/248=1.33；vibeguard 302/97=**3.11**；douyin-mcp 244/50=4.88。

[推断，置信度：高] 全局 bug/decision 比下降到 0.32（绿灯）是双环学习开始产生结构性效果的第一个可量化信号。但必须按项目拆解：harness bugfix/session=2.72 说明**单环修复仍然是主旋律**；x bugfix/session=0.544 是全局最低之一，对应其 expert% 最高——两个指标互相印证：**单环学习密度低的项目，双环成熟度高**。

**双环学习（改变假设/心智模型）的证据**：

[事实] insights 报告中识别的几个明确双环产物：
1. vibeguard paths frontmatter 收窄规则作用域（改变"规则加载范围"的根本假设）
2. harness heartbeat 不每次持久化，改用 `last_heartbeat_at` 动态派生 online（改变"持久状态与派生状态"的心智模型）
3. remem 将 ProjectId 身份模型、pending 失败语义、MCP/API 契约漂移识别为系统性问题并排优先级（改变"bugfix 方式 vs 重构方式"的选择框架）
4. xhh 放弃 NanoBanana Pro 改用 HTML 模板+Chrome headless（改变"可用性优先于理想链路"的架构假设）
5. reddit-monitor 把评论生成从"能说就说"改成"只有有实测经验才说"（改变内容策略的根本约束）

[推断，置信度：中] 上述 5 个双环样本比 0321 版多出 3 个（0321 版列出 3 个），且扩散到了 xhh、reddit-monitor 这样的"运营型"项目。**双环学习从元工具项目开始向内容主力系统扩散**，这是 0321 版未能预测的走向。

**双环学习的结构仍受限**：

[推断，置信度：高] harness（259 session，expert 8.9%）的双环学习证据仍然稀疏。704 个 bugfix 中真正改变根本假设的比例估计 <10%。Apply 层级仍是 harness 的主导操作方式。0321 版"harness 需要一次根本性反思"的建议在 2026-04-08 的数据上**仍然成立，且紧迫性上升**（session +15%，expert% 几乎持平）。

### Bug 高频类型变化分析

   - 验证：三周后看这三类阻力的出现次数是否下降 > 50%

**[推断，置信度：中]** 如果这四个优先级在下一周期落地，delegation 占比应回落到 42-45%，exploration 回升到 12-15%，pair_programming 突破 6%，无效摩擦占比降到 50% 以下。这将是从"带风险的进化"转向"稳定的进化"的临界点。

**[推断，置信度：低]** 若不干预，趋势外推：下一周期 delegation 可能上探 51%，exploration 跌破 5%，心流率跌破 8%，reddit-monitor 模式会蔓延到更多老项目。此时"思考外包化"会从风险转为既成事实，恢复成本显著上升。

### 4.1 认知瓶颈诊断

本轮数据给出的画像与 03-21 那次最大的差别是：**规模扩大了 2.5 倍（1565 → 3919 sessions），但结构性问题不仅没有修复，部分维度还在恶化**。下面三个瓶颈是接下来 12 周必须正面处理的。

#### 瓶颈一：探索饥荒——探索率从 11% 退到 7%，且是 Mirror 唯一的红灯

`[事实]` Mirror 认知镜像显示探索率 **6.6%**（红区），深耕率 24% ✓，碎片化 22% ✗；协作模式分布里 exploration 252 / 3903 ≈ **6.5%**，deep_inquiry 233 ≈ **6.0%**，二者合计 **12.5%**。健康线的参考值是 ≥15%。
`[事实]` 上一版报告（2026-03-21）的 exploration 占比是 **11%**；本轮是 6.6%，**三周内下降了约 40%**。
`[推断]`（置信度：高）这 40% 的下降不是随机波动，而是「规模吞噬探索」的结构性现象——会话总量从 1565 涨到 3919（+150%），绝大部分新增量进了 delegation 和 review 两个桶，说明你把节省下来的时间回灌进了「执行现有规则」而不是「打开新方向」。
`[推断]`（置信度：中）探索饥荒和注意力碎片化（22%）是共因：因为碎片化，你每个时段都只敢做「能快速收尾」的事，而探索天然需要长时间块。

#### 瓶颈二：委派接口精度不足——delegation 49% 但 pair_programming 3%，中间没有缓冲

`[事实]` 协作模式分布：delegation 1914（**49.0%**）、review 1335（**34.2%**）、exploration 252（6.5%）、deep_inquiry 233（6.0%）、pair_programming 117（**3.0%**）、teaching 44（1.1%）、debugging 8（0.2%）。delegation+review 合计 **83.2%**。
`[事实]` 决策:修复比 = 19584 : 6257 = **3.13 : 1**，比 03-21 的 2.4 : 1 提升了；但 insights 报告列出 **7 类高频阻力中 5 类仍是接口契约/路径规范化/并发竞争/配置漂移等无效摩擦**。
`[推断]`（置信度：高）decision/bugfix 比在上升（说明决策数量增长比 bug 增长更快）而无效摩擦类别没有收敛，意味着：**bug 修复效率提升来自「重复踩同一块地雷然后快速绕过」，而不是「系统性消除地雷」**。这是典型的委派接口精度问题——你给 AI 的任务描述没有前置声明接口契约，AI 一次只修一个点，下次换一个项目又犯同类错。
`[推断]`（置信度：中高）pair_programming 只有 3% 是瓶颈的机械成因：你要么「全程亲写」要么「全包给 AI」，中间没有「你先写草案，AI 补齐」或「AI 先写，你逐行审」的缓冲带。这个缺失的缓冲带本来是最能捕捉接口契约漂移的地方。

#### 瓶颈三：无效摩擦未系统消除——5/7 高频阻力属于工程纪律问题，VibeGuard 已建但未落位

`[事实]` insights 报告阻力热点表列出的 7 类高频阻力中，至少 5 类属于无效摩擦：接口契约/类型误解、路径/文件系统规范化、并发/幂等/状态竞争、配置与默认值漂移、校验不完整。剩余 2 类（外部系统受限、可观测性不足）一半可治一半不可治。
`[事实]` vibeguard 项目本身 97 sessions / 633 decisions / 302 bugfixes，远高于同规模工具项目的 bug 密度；说明 VibeGuard 作为工具已经建成但其内部治理本身在吃掉大量认知资源。
`[推断]`（置信度：高）「VibeGuard 已经有 101 条规则 + hooks」和「5 类高频阻力仍在 insights 报告里」这两个事实同时成立，只能解释为：规则与 hook 的覆盖范围、触发点、或作用域 frontmatter 没有真正把关键路径卡死。insights 报告里明确提到 `~/.claude/rules/vibeguard/common/` 缺少 `paths frontmatter` 导致规则被注入到全局——这一条就可能解释 30% 的无效摩擦。
`[推断]`（置信度：中）harness 的 bug 修复密度（704 bugs / 259 sessions ≈ 2.7 bugs/session）显著高于其他项目，是「无效摩擦未治理 + 复杂度集中」共同导致的认知黑洞。

### 4.2 学习策略处方

本节给出 5 条处方，每条严格采用「触发条件 / 行动 / 验证标准 / 完成标志」四件套结构。所有处方均为 `[建议]`，均附前提假设和替代方案。

#### 处方 1：每周保留新方向 Session——打破探索饥荒

`[建议]` 前提假设：探索率低的根因是「没有显式预算」而非「没有兴趣」。替代方案：如果执行 4 周后仍然上不去，改为「每月一次连续 2 天的探索闭关」——用频率换密度。

**触发条件**：每周一早上规划本周任务时；或当连续 5 个 session 都在同一项目同一模式时。

**行动**：
1. 在周任务清单里固定 **2 个 slot** 标记为 `exploration-only`，禁止任何进行中项目的任务占用这两个 slot。
2. 探索 slot 的硬约束：禁止 delegation、禁止 review、必须亲自写或亲自推理至少 30 分钟；允许失败、允许放弃、允许只产出「这个方向不值得」的结论。
3. 探索方向从三类里选一：（a）与 remem/refine 有潜在协同的新技术；（b）你当前 expert 占比 <10% 的领域（按 L2 数据选）；（c）一个你最近 30 天内主动搜过但没深入的关键词。
4. 每个探索 session 结束后强制产出 **一页结论**（markdown 即可），包含：我试了什么 / 我学到了什么 / 我决定是否继续。

**验证标准**：4 周后 exploration 占比从 6.6% 提升到 ≥**12%**；8 周后提升到 ≥**15%**。每周至少有 1 页探索结论文档落盘到 `docs/exploration/`。

**完成标志**：exploration 连续 4 周稳定 ≥15%，且至少有 1 个探索方向转化为新项目或现有项目的新模块。

#### 处方 2：复杂任务强制两阶段协议——提升委派接口精度

`[建议]` 前提假设：委派精度低的根因是「接口契约不在任务描述里」而非「AI 能力不足」。替代方案：如果两阶段协议拖慢节奏超过 20%，退化为「只对 3+ 文件任务强制，1-2 文件直接做」。

**触发条件**：任务涉及 3+ 文件修改；或任务跨模块；或任务涉及并发/状态机/路径处理；或任务需要修改已有公开 API。

**行动**：
1. **第一阶段（Review 前置）**：不允许直接写代码。要求 AI 先输出「假设清单 + 证据 + 未验证项 + 影响面」，你人工确认每一项；如果 AI 想改公开 API，必须先搜出所有调用点。
2. **第二阶段（Delegation 执行）**：只有第一阶段确认通过后才进入执行。执行时 AI 必须一次改完所有相关文件，禁止「先改一个看看」。
3. 两阶段之间的交接产物固化为 spec 文件（即使只有 5 行），落盘到项目的 `docs/specs/` 目录。
4. 执行后必须有 `cargo check` / `npx tsc --noEmit` / `go build ./...` 新鲜输出作为验证证据（W-03）。

**验证标准**：8 周后 pair_programming + deep_inquiry 合计占比从 9% 提升到 ≥**18%**；insights 报告中「接口契约/类型误解」阻力从「高频」降到「中频」；decision/bugfix 比从 3.13 提升到 ≥**3.8**。

**完成标志**：连续 4 周内没有出现「同一类型的接口契约错误在两个不同项目里发生」的情况。

#### 处方 3：接口契约三件套——系统消除无效摩擦

`[建议]` 前提假设：接口契约/路径/并发三类问题可以通过「前置 schema + canonicalize helper + 幂等键」三件套 80% 覆盖。替代方案：如果三件套在某类场景（如 Python dynamic dispatch）失效，降级为「对该类场景强制人工 pair review」。

**触发条件**：新建项目；或项目引入新的外部 API；或项目出现 3 次同类 bug 需要根治。

**行动**：
1. **契约件 1：API 契约测试**。对核心外部 API（Vertex、Reddit、xhs、douyin）各建立一个 contract test，至少覆盖 `systemInstruction`、`parts` 字段集、rate limiter 返回类型这类已在 insights 里点名的坑。测试放 `tests/contracts/`，CI 必跑。
2. **契约件 2：路径 helper 统一**。在每个 Rust/Python 项目的 `core` 层导出 `default_db_path()`、`canonicalize_or_create()`、`tempdir_for_test()` 三个函数，**禁止**业务代码直接 `.join("*.db")` 或调用 `PathBuf::canonicalize()`。这条直接对应 U-11/U-12/U-13/U-14。
3. **契约件 3：发送幂等键**。所有「发帖/回复/评论/发布」动作强制带幂等键，键的生成函数集中在 `core/idempotency.rs`。发送前先写 pending 行并占位，发送后再标记 committed。
4. 每条规则落地后更新 VibeGuard 的对应 rule 文件（`~/.claude/rules/vibeguard/common/`）并补 `paths frontmatter`。

**验证标准**：12 周后 insights 报告中「接口契约/类型误解」「路径/文件系统规范化」「并发/幂等/状态竞争」三类阻力全部从「高频」降到「中频」或「低频」。bugfixes 增速首次低于 sessions 增速（修复密度下降）。

**完成标志**：连续 8 周没有新增因三类问题导致的 bugfix；VibeGuard 对应规则的触发率进入稳定下降通道。

#### 处方 4：harness 认知解压——从 bug 消耗场变成理解升级场

`[建议]` 前提假设：harness 的高 bug 密度（2.7 bugs/session）来自「复杂度 × 审查者幻觉」而非「代码质量差」。替代方案：如果 harness 认知升级与产出速度冲突，将 harness 降级为 trial 阶段产品，从核心项目组降格。

**触发条件**：准备在 harness 上做 review 或 delegation 之前。

**行动**：
1. Review 前置 15 分钟 deep_inquiry：读相关核心代码、画一张数据流图（纸笔即可）、写一句话回答「这个 PR 修的是什么机制」。
2. harness 的模式目标从当前 `delegation 50% + review 35%` 调整为 `deep_inquiry 25% + review 30% + delegation 35% + pair_programming 10%`。
3. 每次 review 后强制写一条「我之前不知道的事」到 `docs/harness/learnings.md`，每条不超过 3 行。
4. 每两周审一次 harness 的 bug 列表，看是否有「同一根因的 bug 出现 ≥2 次」，如有则开一个独立 issue 专门根治。

**验证标准**：8 周后 harness 的 bug 密度从 2.7 降到 ≤**1.8**；harness 里 expert 级 session 占比从当前 23/259 ≈ 8.9% 提升到 ≥**15%**；`learnings.md` 至少积累 16 条记录。

**完成标志**：你能在不翻代码的情况下连续说清 harness 的 3 个核心数据流（任务 spawn / heartbeat / 持久化补偿）。

#### 处方 5：xhh 策略沉淀——把高流量执行变成可复用产品

`[建议]` 前提假设：xhh 占比高但认知收益低的根因是「策略散落在 session 记忆里」。替代方案：如果沉淀压缩了 xhh 产出，退回「xhh 维持现状但明确只做执行，认知资源迁移到 dian」。

**触发条件**：每周五下午，作为本周 xhh 整合时段。

**行动**：
1. 把 xhh 的发布策略（图文 vs 视频的选择标准、Humanizer 触发条件、HTML 模板 vs NanoBanana 降级路径、xhscli vs 手动切换规则）整理成 `xhh/STRATEGY.md` 单一事实来源。
2. 把策略里的硬编码（间隔分钟、频率阈值、候选评分权重）集中到 `xhh/config/policy.toml`，业务代码只读不写。
3. 将 xhh 中已稳定的「候选评分 + 配额 + 幂等发送 + 拒绝原因统计」抽象成可复用模块 `content-scheduler-core`，同时服务 xhh / x / reddit-monitor 三个下游。
4. xhh session 占比从当前 248/3919 ≈ 6.3%（数据口径）/ 或 03-21 声称的 15%（注意力口径）降到 ≤**8%**（注意力口径），节省的时间迁移到探索和 pair_programming。

**验证标准**：12 周后 `content-scheduler-core` 至少被 2 个项目引用；xhh 的 decision/bugfix 比从 1197:331 ≈ 3.6 提升到 ≥**5.0**；xhh 的 STRATEGY.md 首次提交后连续 4 周只有追加没有推翻。

**完成标志**：新的内容项目（如未来的第 4 个内容平台）可以直接复用 `content-scheduler-core`，搭建时间从 2 周降到 3 天。

### 4.4 AI 协作进化路径

| review | 34.2% | 28% | harness 里从形式审查升级为实质审查 |
| deep_inquiry | 6.0% | **≥12%** | remem/refine/vibeguard 的默认模式 |
| exploration | 6.5% | **≥15%** | 处方 1 的硬配额 |
| pair_programming | 3.0% | **≥8%** | 复杂任务的默认模式（处方 2） |
| teaching | 1.1% | **≥3%** | 每周 1 次向 AI 解释核心设计 |
| debugging | 0.2% | 1% | 配合处方 4，harness 的 bug 定位 |

#### 模式切换决策树

当你开始一个新 session 时，按以下顺序问自己：

```
1. 这个任务我能不能用 3 句话完整解释它的目标 + 接口 + 验证方法？
   ├── 不能 → deep_inquiry（先读代码、先问 AI 假设清单）
   └── 能 → 继续

2. 这个任务涉及多少文件？
   ├── 1-2 个 → delegation 允许（简单任务）
   ├── 3-5 个 → 强制两阶段协议（处方 2）
   └── 6+ 个 → /vibeguard:interview → spec → 再执行

3. 这个任务是否涉及以下高风险场景？
   （公开 API 变更 / 状态机 / 并发 / 路径处理 / 外部平台发送）
   ├── 是 → pair_programming（AI 出草案，你逐行审）
   └── 否 → 继续

4. 这个任务是否属于核心项目（remem / refine / vibeguard）？
   ├── 是 → pair_programming 或 deep_inquiry
   └── 否 → 继续

5. 这个任务是否是探索型？
   ├── 是 → exploration（禁止 delegation，必须亲写）
   └── 否 → delegation（常规执行）
```

#### 具体切换时机

- **从 delegation 切到 pair_programming**：连续 3 个 delegation session 后「我好久没自己写代码了」的感觉浮现时 / 任务里出现「状态机」「生命周期」「并发」关键词时 / 任务描述里写不出接口契约时。
- **从 review 切到 deep_inquiry**：review 时你发现「我不确定这是对的」≥2 次 / 对同一模块 review 了 3 次仍说不清核心逻辑 / review 产出的意见全部是风格/格式类。
- **从任何模式切到 exploration**：周一/周五的探索 slot 时段 / 遇到「我不知道该用什么工具」场景 / 连续 5 个 session 都是同一项目同一模式时。

### 4.5 十二周成长计划

#### 第一阶段：清除无效摩擦 + 重分类 + 启动探索（第 1-4 周）

**主题：先把地面上的坑填平，再谈新方向**

**第 1 周：基线测量 + VibeGuard 作用域修复**
本周核心是给 12 周计划打桩。第一步：跑一次 cognitive-portrait 生成本周的模式分布、Dreyfus 分布、bug 密度、项目 session 数，作为后续对比基线。第二步：修复 `~/.claude/rules/vibeguard/common/` 下规则的 `paths frontmatter`，按 insights 里点名的「规则作用域过宽导致 token 爆炸」问题解决一次。第三步：建立 `docs/cognitive-portraits/weekly/` 目录，本周基线报告落盘。
**验证点**：基线报告生成 + VibeGuard 规则 frontmatter 修复 commit；`cargo check` 或对应构建命令通过。

**第 2 周：接口契约三件套启动（处方 3 第一批）**
本周聚焦契约件 1 + 契约件 2。为 Vertex / Reddit / RateLimiter 三个最高频的外部 API 各写一个 contract test，落到 `tests/contracts/`。同时在 harness / remem / x 三个项目的 core 层各导出 `default_db_path()` 与 `canonicalize_or_create()` helper。**这一步本身就能检测出 3-5 个历史遗留的路径处理 bug**，逐个修复。
**验证点**：3 个 contract test 全绿；3 个项目的 path helper 已被业务代码调用替换 `.join("*.db")` 或原生 `canonicalize`。

**第 3 周：other 重分类脚本 + 探索 slot 启动**
本周做两件事。第一件：为 1861 other sessions 写一个重分类脚本，按关键词分成 `looper`、`pr-review`、`x-queue`、`ops`、`unknown`，输出一份分布 CSV。第二件：第一次启动探索 slot，选择 1 个新方向（建议：与 refine 协同的认知数据可视化方向），周五下午完整跑一次探索 session 并产出一页结论。
**验证点**：other 分布 CSV 落盘；第一页探索结论落盘到 `docs/exploration/`。

**第 4 周：第一阶段复盘**
对比第 1 周基线和第 4 周数据。关注四个数字：exploration 占比是否进入 10%+？接口契约类 bug 是否 0 新增？path helper 是否覆盖 3 个项目？VibeGuard token 占用是否下降？如有某个数字卡住，分析是处方设计问题还是执行问题，调整后进入第二阶段。
**验证点**：第一阶段复盘报告落盘；至少 2 个核心指标有可量化改善。

#### 第二阶段：harness 认知升级 + xhh 沉淀 + remem 收敛 + 内容审计（第 5-8 周）

### 4.6 风险与兜底

| 风险 | 概率 | 触发信号 | 兜底方案 | 底线 |
|------|---:|------|------|------|
| 探索 slot 被紧急任务挤占（延续 03-21 未解） | 高 | 连续 2 周 exploration <10% | slot 固定安排在周五下午（最不可能有紧急需求的时段）；在 todo 工具里标记 `locked` | 两周内至少 3 次探索 session，允许单周为零但不允许连续 2 周为零 |
| pair_programming 不自然，效率感下降被放弃 | 中高 | 连续 2 周 pair_programming 占比下降 | 前 4 周只在 vibeguard（最均衡的项目）练 pair_programming，习惯后再推广 | 即使 pair_programming 不适应，deep_inquiry 占比必须提升到 ≥10% 作为替代 |
| 接口契约三件套误报太多，反而增加摩擦 | 中 | hook 触发率 >30% 或被频繁临时禁用 | hook 前 2 周设为 warning 模式（只提醒不阻断），第 3 周根据误报率再决定是否切换 blocking | 误报率 >30% 的规则降级为 warning 直到调优完成；不允许「批量 skip」 |
| harness 认知升级与产出速度冲突 | 中 | 连续 4 周 harness bug 密度未下降 | 降级 harness：从核心项目组降格为 trial 阶段，只维持最小功能 | 宁可让 harness 慢 20%，也不允许 bug 密度回到 2.7 以上 |
| xhh 策略沉淀压缩产出 | 中低 | 连续 2 周 xhh 发布量下降 >30% | 回退到 xhh 维持现状、只做执行；认知资源迁移到 dian 或探索 | 保留 xhh 最低发布量不被动波动 |
| 12 周内 Mirror 三指标全部卡 🔴/🟡 不动 | 中低（如果前 5 项都翻车） | 第 6 周中检发现无改善 | 中止全部处方，召开一次「为什么 03-21 处方也没执行」的元复盘；重写处方范式 | 不允许在没有根因分析的情况下进入下一个 12 周计划 |

### 4.7 本章三分离总结

**事实**：
- 探索率 6.6%（03-21 时 11%，三周内退化 40%）
- 委派 49.0% + 审查 34.2% = 83.2%，中间缓冲（pair_programming 3.0%）严重不足
- 5/7 高频阻力是无效摩擦，VibeGuard 已建但作用域未落位
- decision/bugfix 比提升到 3.13:1（从 2.4:1），但 harness bug 密度仍 2.7/session
- Mirror 三指标：认知深度 🟡、战略广度 🔴、协作效能 🔴

**推断**：
- 规模扩张（+150% sessions）吞噬了探索空间（置信度：高）
- 03-21 的 5 条处方中至少 3 条未实际执行，缺少追踪机制（置信度：中）
- 无效摩擦未收敛的根因是 VibeGuard 规则 frontmatter 作用域问题（置信度：中高）
- pair_programming 3% 是「没有中间缓冲带」导致的接口契约漂移的主因（置信度：中）

**建议**：
- 5 条处方聚焦：探索配额 / 两阶段协议 / 契约三件套 / harness 认知解压 / xhh 沉淀
- 12 周三阶段：清摩擦 → 深耕收敛 → 协作重塑
- 核心目标（必须达成其中至少 5 个）：exploration ≥15% / pair_programming ≥8% / delegation ≤38% / deep_inquiry ≥12% / decision:bugfix ≥3.8 / harness bug 密度 ≤1.8 / Mirror 至少 1 🟢 / 5 类无效摩擦降至中/低
- 必须在第 12 周前为 cognitive-portrait 工具增加「处方追踪模块」，解决「执行情况只能推断」的元瓶颈
