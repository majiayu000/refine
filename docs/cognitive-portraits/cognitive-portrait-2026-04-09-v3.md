#### 多臂老虎机 / James March 理论框架

[推断，置信度：中] 在多臂老虎机模型下，最优探索比与环境变化速率成正比。对于快速变化的 AI 工具生态，文献常见的经验参考区间是 **10-20%**。James March(1991) 在组织学习经典论文中指出：过度利用(exploitation)会形成"能力陷阱"——短期效率最大但长期适应性丧失；过度探索则形成"失败陷阱"——永远在试错不积累。
[推断，置信度：高] 当前 6.4% 的纯探索率位于 **过度利用区**（低于 10% 下限）。广义 12.4% 勉强进入健康下缘，但扣除 deep_inquiry 中被锁死在 om/remem 两个项目的部分（43+14=57 次，占全部 deep_inquiry 的 24.5%），真正意义上"向未知领域扩张"的探索会话 < 8%。
[推断，置信度：中] 与基线 03-21 的 11% → 6.4% 对比（-4.6pp），说明**探索率在绝对萎缩而不是仅相对稀释**：基线时期 exploration = 1565 * 11% ≈ 172 次，当前 252 次。分子只增加了 80 次（+46.5%），但分母增加了 2354 次（+150.4%）——**新增的 94.5% 会话都不是探索**。

#### 结构洞识别（Burt 理论）

Ronald Burt(1992) 的结构洞理论：两个群体之间如果只通过少数节点连接（或根本不连接），这个断裂点就是"结构洞"。在认知组合里，结构洞意味着两组项目之间可以桥接但目前孤立——谁填补这个洞谁就获得"知识套利"收益。

**结构洞 1：X 内容运营系统 ↔ harness 调度基础设施**
[事实] x 的 677 次 delegation 指向"候选评分 + 配额 + 幂等发送"；harness 的核心技术是"pending 状态机 + owner/reconciler + 启动恢复扫描"。
[事实] 基线 03-21 没有列出 x 项目（当时 x 不在雷达内），所以结构洞 1 是 18 天内新形成的洞。
[推断，置信度：高] 这两个项目的**技术底层几乎相同**（SQLite 状态机 + 幂等 + 节流），但在 insights 报告中没有看到 x 引用 harness 的状态机模式、也没看到 harness 引用 x 的配额规则体系。如果桥接，harness 可以拿到 x 的规则表达力，x 可以拿到 harness 的 owner/reconciler 防僵尸任务机制。

**结构洞 2：remem/refine 元认知层 ↔ x/harness/xhh 主力层**
[事实] remem expert 率 39.4%，refine 17.4%，但这两个项目的洞察没有直接反馈给 x/harness/xhh——insights 报告原话是"refine 能告诉你 xhh 的 expert 率低，但没有机制确保这个洞察转化为行为改变"。
[推断，置信度：高] 这是 03-21 基线已经识别的洞，18 天内**没有填补**。基线建议"refine 的分析结果自动生成 vibeguard 规则"，但从数据上看 vibeguard 的规则数增长（漫长尾部的 16 次 exploration）与 refine 的洞察输出之间没有可追溯的关联。结构洞仍然开放。

**结构洞 3：reddit-monitor ↔ om 数据管道**
[事实] om 中"多源扫描周报"（~/.claude/projects + git + 多 repo 并行）已经形成成熟数据聚合模式；reddit-monitor 有 236 次会话在做"候选筛选 + 真实性判定 + 拒绝原因归因"。
[推断，置信度：中] 这两个项目的数据模型高度相似（事件流 + 多源扫描 + 规则归因），但 insights 报告里没有看到任何复用迹象。reddit-monitor 的数据能力远低于 om，但因为不同业务场景没有桥接。

**结构洞 4：vibeguard 规则层 ↔ 非基础设施项目**
[事实] vibeguard 的 101 条规则中很多是"通用 AI 防幻觉规则"，但 x/xhh/reddit-monitor 的规则误杀、契约误解、TOCTOU 问题在 insights 里被单独归类为"阻力热点"，而没有被引用到 vibeguard 规则里。
[推断，置信度：中] 结构洞 4 的表现形式是"**规则生产者与规则消费者的反馈断链**"：vibeguard 生产规则→被注入所有项目→但项目里发现的新阻力模式没有回流到 vibeguard。

### 4.2 处方清单

#### 处方 1：强制探索预算（解决探索率过低）

**触发条件**：每周一上午 9:00-10:30 和每周四下午 14:00-15:30，日历硬预留两个 90 分钟块，任何非紧急任务不得占用。触发信号：当周 mirror 统计的 exploration 占比 < 10%，下周必须执行且时长加倍。

**行动**：
1. 每个 90 分钟块必须进入**一个从未进过的仓库/领域**（不是 top5 项目的新模块，是全新坐标）。候选池：opensource/、work-infra-vie/、work-infra-bus/ 这类只有 1-2 sessions 的陌生项目
2. 90 分钟切三段：30 分钟只读（架构 + 最近 10 个 commit）、30 分钟提 3 个"如果我是这个项目 owner 明天会做什么"的假设、30 分钟写 1 个最小可验证实验或 1 份 200 字的"陌生领域入场笔记"并提交到 `docs/exploration/<date>.md`
3. **禁止在探索块里写生产代码** — 写了就算作弊，因为会被 delegation 反射劫持
4. 每次结束后在 remem 记录一条 type=discovery，topic_key="exploration-<project>"

**验证标准**：
- 4 周后（2026-05-07）cp_data_mirror 中 exploration 占比 ≥ 12%
- 8 周后 exploration 占比 ≥ 15%
- 12 周后 exploration 占比稳定在 15%-18% 区间
- 每周必须有 ≥ 1 个新项目坐标出现在 remem 的 discovery 类型记录里

**完成标志**：连续 6 周 exploration 占比 ≥ 12% 且每周至少 1 条新仓库 discovery 记录不中断。

**如果放弃会发生什么**：探索率稳在 7% 甚至下滑到 5%，碎片化从 22% 爬升到 28%+，你会在新项目诞生时继续堆到 other 桶里而不是进入深度观察。替代方案：若 12 周都做不到 12%，下线此处方，改为"每两周一次半天探索"的低频高强度版本。[建议] 前提假设：你的日历自由度允许硬预留两个 90 分钟块；若工作强制打断，改为早上 6:30-8:00 的私人时段。

#### 处方 2：接口契约三件套（解决高频接口误解阻力 / 摩擦密度 3.1）

**触发条件**：任何涉及跨 2+ 文件、跨进程、跨 crate、跨服务的委派任务，在派给 AI 之前必须先写三件套。触发信号：委派 prompt 长度 < 300 字且任务涉及跨模块 → 强制 abort 并补齐三件套。

**行动**：
1. **输入契约**：明确这次改动的 input 来源是哪个函数/接口/HTTP endpoint，字段清单，类型，边界值，空值策略
2. **输出契约**：改完之后调用方会看到什么（返回值、错误码、副作用），哪些字段会变、哪些不能动
3. **验证命令**：一条 60 秒内能跑完的命令证明这次改动成功（cargo test --lib xxx / curl localhost:9800/xxx / python -m pytest tests/test_xxx.py -x）
4. 三件套写完后才能把 prompt 发给 AI。三件套不能写 > 意味着任务定义不清，自己先想清楚或进入 deep_inquiry 模式

**验证标准**：
- 4 周后 cp_data_mirror 中 摩擦密度 ≤ 2.5（从 3.1 下降 0.6+）
- 8 周后 摩擦密度 ≤ 2.0
- 12 周后 摩擦密度 ≤ 1.8 且 bug/决策比维持 ≤ 0.35
- 在 harness / remem / vibeguard 三个核心 Rust 项目中，接口契约三件套的记录比例 ≥ 80%（通过 git log 的 commit message 体现，或 docs/contracts/ 目录记录）

**完成标志**：连续 4 周摩擦密度 ≤ 2.0 且接口契约三件套在 top3 项目里覆盖率 ≥ 80%。

**[反直觉]** 这条处方看起来会让你"慢下来"（每次委派前多花 5 分钟），但实测 5 分钟的契约写作能省掉 20+ 分钟的来回返工。反直觉点在于：你会觉得"我知道要做什么，直接派给 AI 更快"，但摩擦密度 3.1 证明你**不知道**。[建议] 前提假设：你能接受"写契约比直接派任务感觉慢"的心理不适；替代方案：前两周先只做"验证命令"一件套，观察摩擦密度是否下降，再逐步加上输入输出契约。

#### 处方 3：项目内核抽取（解决跨项目重复阻力 / Dreyfus 下沉）

**触发条件**：每月最后一个周日晚上，或当 cp_data_projects 里新增项目数 ≥ 3 个时。触发信号：当月新项目诞生数 ≥ 3 或已有项目新增会话 < 5 个但被修改。

2. 把这些模式提取到一个新的 crate/module：例如 `~/Desktop/code/AI/tools/kernel/` 或继续沿用 refine 下的 core 包
3. 每月抽取 1-2 个模式，**不求快，求稳** — 抽取的标准是"下一个项目能直接 import 复用"

```
  │         出口条件：能写出三句话 → 回到 Q2
  │
  └─ 是 ──▶ Q2: 这个任务是否涉及 3+ 文件 / 跨模块 / 并发 / 状态机 / 持久化 schema？
              │
              ├─ 是 ──▶ 进入 review 模式
              │         （让 AI 先输出 3 条假设 + 1 份改动清单，你逐项确认）
              │         出口条件：假设全部确认 → 进入 Q3
              │
              └─ 否 ──▶ Q3: 是否涉及高风险场景（认证/支付/密钥/DB 迁移/远程部署）？
                          │
                          ├─ 是 ──▶ 进入 pair_programming 模式
                          │         （AI 写一段，你读一段，禁止连续 > 50 行不审核）
                          │
                          └─ 否 ──▶ Q4: 是否是熟悉的重复模板工作（CRUD / 脚手架）？
                                      │
                                      ├─ 是 ──▶ delegation 模式（但必须带契约三件套）
                                      │
                                      └─ 否 ──▶ 回到 Q1 重新审视
```

**每个决策节点的判定规则**：
- Q1 判定："3 句话"是硬标准，不能超 3 句，超了就是自己没想清楚
- Q2 判定："3+ 文件"是客观计数；"跨模块"看 import 是否跨越顶层模块边界；"状态机"看是否有显式的状态枚举
- Q3 判定：认证/支付/密钥/DB 迁移是硬清单，任何一项命中必须 pair_programming
- Q4 判定：只有你已经写过 ≥ 3 次的模板才算"熟悉模板"

**[误用反例 1] delegation 陷阱**：
你收到"在 harness 里加一个 webhook 通知"这个需求 → 感觉很简单 → 直接派给 AI → AI 改了 4 个文件 → 你快速合并 → 结果线上 webhook 和现有的 task stream 冲突 → 回滚 → 你怪 AI "没考虑周全"。
**真相**：这个任务命中 Q2（跨 4 文件）+ Q3（远程触发），本应进入 review + pair_programming，但你跳过决策树直接 delegation，这就是委派陷阱。

**[误用反例 2] 假 deep_inquiry**：
你花 2 小时"思考架构"，但全程在让 AI 给你解释概念，而不是自己提问挑战。这是伪装成 deep_inquiry 的 delegation。判定标准：deep_inquiry 里你应该是**提问者**，AI 是被质疑的对象；如果 AI 在给你讲课，那是 teaching 模式（而且是反的，你是学生）。

[建议] 把决策树打印出来贴在显示器旁边，前两周每次开始任务前看一眼，第三周开始可以内化为直觉。替代方案：做成 alfred/raycast workflow 按 hotkey 弹出决策树。前提假设：你愿意承受"每次任务多花 30 秒判断"的摩擦成本。

### 4.5 12 周成长计划

前 4 周 = 止血期（直接打委派反射 + 摩擦密度）
第 5-8 周 = 系统建设期（固化契约 + 内核抽取）
第 9-12 周 = 复利期（跨项目应用 + 元复盘）

| 周次 | 主题 | 关联处方 | 关键行动 | 验证点（周末自检） |
|---|---|---|---|---|
| W1 | 探索块落地 | P1 | 周一、周四各 1 个 90 分钟探索块，进入 2 个陌生项目 | 周日查 remem 是否有 ≥ 2 条 discovery 记录；exploration 占比 ≥ 9% |
| W2 | 契约三件套导入 | P2 | 所有跨文件委派任务写契约；数 commit 中写了契约的比例 | 周日查 top3 项目委派任务的契约覆盖率 ≥ 50% |
| W3 | 决策树实战 | P1+P2+P4 | 每次任务开始前看决策树；记录 misfire 次数 | 周日统计 delegation 误用（命中 Q2/Q3 但仍 delegation）≤ 3 次 |
| W4 | 止血期复盘 | 全部 | 对照 W1-W3 所有处方指标，做一次完整自检 + remem 总结 | **里程碑**: exploration ≥ 10%、摩擦 ≤ 2.8、delegation ≤ 46% |
| W5 | harness 深度专项启动 | P4 | 周二/周五 harness 2h pair_programming 块 + 全链路 review 画图 | harness expert 计数 ≥ 25；docs/harness-arch/ 有新图 |

| W8 | 系统建设期复盘 | 全部 | 对照 W5-W7，检查系统是否真的在建立而不是又成了手忙脚乱 | **里程碑**: 摩擦 ≤ 2.2、exploration ≥ 12%、pair_programming ≥ 14% |

| W11 | 元复盘周：质疑自己 | 元认知 | 读本次 12 周所有 remem 记录 + mirror 趋势，找 3 条打脸的决定 | 写一篇 "12 周元复盘" markdown，≥ 1500 字 |

**阶段复盘点**：
- **W4 复盘（止血期结束）**：若 exploration < 10% 或 摩擦 > 2.8，说明处方 1/2 没落地，进入"应急模式" — 砍 harness 深度专项，集中火力把止血期两项指标打下去再启动后续周
- **W8 复盘（系统期结束）**：若 kernel 模块 < 2 个或内容策略文档 < 3 份，说明系统建设没产出，降低 W9-W12 的野心，改为"每周只推 1 个指标"
- **W12 复盘（复利期结束）**：无论是否达成，都要写 1500+ 字的元复盘，判断下一个 12 周的主题

**[建议]** 前提假设：12 周里没有大的外部中断（出差、病假 > 2 周、项目紧急上线）；若有中断，把该周标记为"黑洞周"并顺延一周。替代方案：如果 W4 止血期没达成，暂停 12 周计划，只做 P1+P2 两条处方，跑 8 周后再决定是否重启 12 周计划。

### 4.6 风险与兜底

| 风险 | 概率 | 触发信号 | 兜底方案 | 底线 |
|---|---|---|---|---|
| 处方 1 探索块被紧急任务吞噬（外部打断） | 高 | 连续 2 周 exploration < 9% 且理由都是"临时任务打断" | 把探索块迁移到早上 6:30-8:00 私人时段；若仍被吞噬，降级为"每两周一次半天探索" | 无论如何每月至少 2 次探索块，每次 ≥ 60 分钟；底线数据：exploration ≥ 8% |
| 处方 2 契约三件套变成形式主义（只写不思考） | 中 | 契约写了但摩擦密度 4 周后未下降（仍 ≥ 2.8） | 从"写契约"改为"口述契约给 AI"（让 AI 先复述目标和验证方法，你确认后才动手） | 至少保留"验证命令"一件套，其他可简化；底线数据：摩擦密度 ≤ 2.8 |
| 处方 3 内核抽取导致过早抽象（违反 U-02 三行重复规则） | 中 | kernel 里出现"只被 1 个项目使用的模块"或"抽出来后又 fork 回去" | 立即下线该模块，回到"等第 3 次重复再抽"的规则；引入"抽取冷静期"：抽取提案必须在 remem 里放 7 天再动手 | 允许 kernel 停留在 ≤ 2 个模块；不追求数量 |
| 处方 4 harness 专项变成又一次 delegation 狂欢 | 高 | harness 深度块里 delegation 占比仍 > 40% | 强制 harness 深度块只能 pair_programming，关闭 delegation 入口（把 AI 切到只读模式） | 即使 pair_programming 没做到，也要保证 harness 每周产出 ≥ 1 条 remem 记录 |
| 处方 5 内容策略文档没人看（只写不用） | 中 | 策略 ADR 写完后 2 周内没有任何人（包括自己）引用 | 把 ADR 从 markdown 改为每周一次 5 分钟的语音自述 + whisper 转文字 | 至少保证每月 1 次的横向对比存在，形式不限 |
| 12 周都没成效，整体方向错了 | 低 | W8 里程碑两项同时未达成 + 摩擦密度反而上升 | 停止所有处方，回到 03-21 基线，只保留 mirror 日报 + 每周一次 /vibeguard:stats 复盘，跑一个月"裸奔期"再评估 | 无论如何保留 mirror 每日统计数据流；数据不能断 |
| 倦怠 / 失焦 / 心理阻力累积 | 中 | 连续 3 天对处方清单产生强烈抵触情绪，或主动"忘记"执行 | 立即暂停 2/3 的处方，只保留最轻的 1 条（建议只保留 P1 探索块）；进入 1 周休整期 | 休整期不得超过 2 周；期间 mirror 数据照常收集 |
| 数据质量不可信（cognitive-portrait 本身有 bug） | 低 | 两周内连续出现 mirror 数据异常跳变 ≥ 3 次 | 暂停所有以"指标驱动"为前提的处方（P1/P2/P4），只保留"行为驱动"的处方（P3/P5）；同时修复 refine/cognitive-portrait 的数据管线 | 保留 remem + git log 作为 backup 真相源 |

**兜底原则总结**：
1. **数据优先**：任何时候 mirror 数据不能断 — 哪怕所有处方都失败，数据流也要保持
2. **最小保留**：如果整体崩溃，至少保留 P1（探索块）和 mirror 数据 — 这是重启的最低基座
3. **止损时间窗**：任何处方执行 4 周没有正向信号，必须下线或大改 — 不要坚持错的方向 12 周

[建议] 上述兜底原则应该在 W4/W8/W12 三个里程碑时刻被朗读一次（对自己口头复述），而不是只写在文档里；前提假设：你愿意把"朗读"作为一种仪式性的自我校准；替代方案：如果朗读感到尴尬，改为"写在当周 remem 记录的开头"作为提醒锚点。

[建议] 风险清单每 4 周重新评估一次（W4 / W8 / W12）；前提假设：你能诚实地面对"我没做到"而不是美化数据。替代方案：如果自检诚实度低，请一个外部人（例如写在 GitHub issue 里）做周度 check-in。
